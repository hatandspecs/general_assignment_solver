1. Import the ballpark

A hand-built starting assignment: CSV or JSON, columns project_id, person_id, month, hours, locked (hours_assigned works for hours; locked is optional). It is allowed to be partial and to break the rules — over capacity, over a cell's bounds, too many projects at once. Audit reports every violation without writing anything; Import loads it anyway, because pulling an infeasible starting point back to feasibility is what step 3 is for.

One kind of problem the solver cannot fix: a project/person/month with no eligible Bounds row has no variable in the model at all, so those rows are reported and skipped. Tick the box below to add permissive bounds and open those cells — that is a real staffing decision, so it never happens silently.

2. Tweak and lock

Edit the Allocation table in Grist — open it from the page list on the left. Change any row's hours_assigned, and tick locked to pin a cell so step 3 cannot move it. Hand-edits are picked up automatically: the next solve saves them as their own iteration first, so they are recoverable even if the solve goes badly.

The sweeps below are the ones that are tedious cell by cell. With no filters they match the whole open horizon. Locking a zero-hour cell pins it empty, which is why "only cells with hours" is on by default.

3. Solve

Takes the working assignment as its starting point, holds every locked cell exactly where it is, and re-optimizes the rest against capacity, bounds and the spend targets. If no assignment can satisfy the locks and constraints together, this writes nothing and reports which constraint or lock is responsible.

Adherence is how hard the solver tries to keep what you gave it. At free the ballpark only breaks ties between equally good plans; at exact it is reproduced almost literally, which can overshoot the spend targets this tool exists to hit. Use exact to find out whether your ballpark is reachable at all, not to produce a plan to send out.

4. Iterations & going back

Every import, hand-tweak, solve, lock sweep and commit is saved as a numbered iteration. Restoring one copies its cells back over the working assignment and appends the result as a new iteration — nothing later is deleted, so going back and changing your mind again costs nothing.

The objective column is not comparable between rows. Part of it measures distance from whatever the assignment held when that solve started, so each iteration is scored against a different reference point — a lower number does not mean a better plan.

5. Export work assignments (commit)

Sends out the working assignment as it stands — the plan you approved in step 3, not a fresh solve that might differ from it. Permanently merges this cycle's Pre_Assignments into Bounds and clears that inbox. If the working assignment holds tweaks that have not been through a solve, this refuses and asks you to solve first, since those numbers have never been checked.

6. Bounds-shaped pre-assignments (optional)

The other, narrower manual input: an hour range per project/person/month rather than a number — "put Alice on this project for 40–80 hours, I don't care exactly how many". JSON, shaped like Bounds rows. These are real constraints, so unlike a ballpark they must be self-consistent, and step 5 merges them permanently into Bounds. Use step 1 instead for an actual assignment you want the solver to start from.
